02 · The problem

Every supplier scenario had to be built by hand.

To test one price, one cancellation rule, one refundability flag, you first had to fabricate the supplier's entire call chain — and make every link agree with the others.

Search→ Packages→ CancellationPolicy→ PreBooking→ Booking→ GetOrder→ CancelOrder + contract + fresh apiKey + markup rules
½–1 day
Per scenario · estimated

Miss one rateKey, one booking id, one price — and the scenario fails three services downstream, silently.

Land the cost, not the mechanics. The point: this was skilled, slow work, and it had to be redone for every variation.

03 · What it does

One form. A complete, wired scenario.

The one sentence to say out loud: the core app never knows the difference — we just change where the contract points. If asked about the fourth box: SMF creates the markup conditions under the Static and Dynamic Markup rules and binds them to the scenario's apiKey, or to the contract when no apiKey is created. Teardown removes them again.

The same thing, without the UI. The Java regression suite provisions its own test data, runs against it, and tears it down when the run ends.

If they ask "who uses it" — this is the slide to slow down on. The API is the bridge to qaBackend_Enigma. The business-rules line is the one non-obvious capability: it means a scenario can test pricing behaviour, not just what the supplier returned.

06 · Next

Where it goes from here.

Step 1

Into tajawal, as a service

The code sits on a personal GitHub account and runs on laptops. Move it under the tajawal org and deploy it as a service — team-owned, always on, one URL for everyone.

Step 2

Into the pipeline

With a hosted URL, the run-template endpoint goes into regression — the suite provisions and cleans up its own test data on every run.

Ongoing

More suppliers

Each one is the same shape: templates, a field map, a small plugin. New suppliers have gone in without touching the engine.
